## Installed-app API crash follow-up (intermediate package)

Latest APK: `Chorium-157.0.8103.15-Android-arm64-20261102-Pixel-site-fix.apk`.
SHA-256: `409d8b831c8c6719c8780c8ddb60d6ba769149ccf24534903f8b0805f5664a5b`.
This includes both fixes below and supersedes the earlier packages.

The user's normal profile exposed another bug: Chromium terminated page
renderers repeatedly with bad IPC reason 123, because no browser binder was
registered for `blink.mojom.InstalledAppProvider`. This embedder does not
implement installed-app detection but Blink exposed its API. App startup
now disables the `InstalledApp` Blink feature, so websites can detect the API
as unsupported instead of crashing their renderer. IPC validation and the
sandbox remain enabled. Existing disabled-feature entries are preserved.

The new real-app regression page checks the API through normal JavaScript
feature detection and verifies the page remains alive and navigation works.
It reproduced `Target crashed` before the fix and passes after installation.
`tools/patch_android_installed_app.py` applies the equivalent Java bytecode
change after the two helpers below. Original signer, 16 KB alignment, CRC
and all 512 unchanged non-DEX payload entries were verified again. This
remains a Java repackage with matching source, without a native/GN build.

## High refresh rate follow-up

The latest APK is `Chorium-157.0.8103.15-Android-arm64-20261102-Pixel-120Hz.apk`,
SHA-256 `8197f97d5e22102803c61128138260138927a6206af892755d6fa16db43c1480`.
It includes the renderer compatibility fix below and removes the page's 60 fps cap.

Android granted the app 120 Hz and the compositor trace recorded 8333 us
vsync/renderer BeginFrames, but page animation measured 60 fps. Matching
[Chromium 157 source](https://github.com/chromium/chromium/blob/157.0.8103.15/cc/base/features.cc)
enables `ThrottleMainFrameTo60Hz` by default on Android. ChoriumActivity now
disables that feature before native startup; child renderers inherit it.
Other disabled features are retained. The existing real-page frame-rate test
now measures **120 fps on the 120 Hz Pixel**. No test threshold was weakened.
This allows more animation work and can consume more power on high refresh
rate displays; idle pages retain Chromium's normal scheduling.

Repackaging also runs `tools/patch_android_frame_rate.py` after the renderer
helper below. Signature, alignment, CRC and all 512 unchanged native/resource/
asset payloads were verified again. No native libraries or upstream Chromium
code were changed, and this was not a full GN/native or Error Prone build.

The earlier compatibility-only APK and its results below remain historical.

Final full Pixel suite with network: **29 tests, 27 pass, 2 desktop-only skips,
zero failures**, 148 seconds. The suite measures 120 fps again; all four
address tests, Tor routing, all popup cases, downloads/uploads, site-data
persistence/clearing and isolated renderer UID checks pass. Logs retained in
`C:\me-tor\Chorium\validation\pixel-full-120hz-suite-20261102.log` and
`pixel-fps-fixed-20261102.log`.

The October APK launched its UI on Pixel 11, but page renderers repeatedly
aborted in `content/app/android/javaless_child_process_service.cc:160` with
`Failed to initialize native`. This phone runs SDK 37 with 4096-byte pages.
Chromium selected `NativeOnlySandboxedProcessService`, bypassing the
`JNI_OnLoad` entry point that registers Chorium's initialization hook.

`ChoriumApplication.attachBaseContext` now configures Chromium's public
`ChildProcessCreationParams` API once in the browser process, explicitly
choosing Java sandboxed services with `forceNativeSandboxedService=false`.
All other creation parameters retain their previous defaults. Child services
remain isolated, and real sandbox UID checks pass. Tor/proxy policy is unchanged.

The source contains the normal Java fix. To ship/test it without fetching and
compiling Chromium again, this release also applies the equivalent method to
the original APK's decoded Java bytecode. The repackaging helper validates the
Application startup anchor, public child-service API and PROCESS_CHILD constant
before inserting the method. It refuses already-patched or unexpected input.

  `b858cff5b6bae8b61220165c4ade82c7fc8120768a8be74fe56b4395e4f979db`.

Workflow: decode the original with Apktool `d -r`, run
`tools/patch_android_renderer_compat.py <decoded-dir>`, rebuild with Apktool,
zipalign, and sign with the same original certificate. Verify signature,
alignment and CRC. Compare every original non-DEX/non-signature payload entry
against the rebuilt APK: all 512 native/resource/asset entries, including the
manifest and browser.wasm, match exactly. Do a normal source/GN build when the
Chromium checkout is available; this compatibility repackage was not a full
GN/native rebuild and did not run Java Error Prone.
